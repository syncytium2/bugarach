# Murderboard run — docs/RESET.md

## What was at stake

The lead document for a project reset is the one page that gets quoted without being
re-checked. This repo has already produced two status documents — `lanes.md` and
`webapp_completion_plan.md` — that went stale while continuing to read as current, and a
whole session's work was spent correcting them. A third one written the same way would
have been worse than none, because it would carry the authority of a reset.

The review found that failure already happening **in the draft**. Four of the counts it
asserted about the project's own state — open pull requests, active session claims,
worktrees, prunable worktrees — were **wrong by the time they were checked**, roughly an
hour after being written, because other sessions were still landing work. Not
approximately wrong: 3 against 4, 5 against 7, 10 against 13, 6 against 8.

That is the finding worth carrying out of this run. **A lead document must not quote
volatile state.** The fix was not to correct the four numbers, which would have been
stale again by delivery; it was to delete every count and name the command that produces
it. What stayed are decisions and constraints, which age slowly.

The second finding of the same family: the draft **described in prose a comparison the
project had already drawn**. `docs/learned/two_decisions.png` panel B shows every
detector's score moving under the fitted background, and the repo's own standing rule is
*"if a finding is visual, render it before writing about it."* The figure now leads that
section. Checking it also caught something the prose would have inherited silently —
**panel C of that figure carries a claim the project has since withdrawn**, that the
ranking is unchanged from 0.4 s to 2.0 s. The document now cites A and B and says not to
cite C until the figure is regenerated.

## What would validate this

The document is checkable by construction: every quantity in it recomputes from a named
file in the tree, and the verify pass did recompute them rather than eyeball them. The
claim that it will not go stale is the one that cannot be tested today — it is tested by
whether the next session that reads it finds it true. The structural bet is that
decisions age slowly and counts do not, so counts were removed.

## How this generalises

Two rules that are not specific to this artifact:

- **A count in a document is a claim with a half-life.** Verify it, and then ask whether
  it should be in the document at all. In a repo with concurrent sessions, the half-life
  can be shorter than the drafting time.
- **When the project has already drawn the thing, cite the drawing — and review the
  drawing.** Reusing a figure inherits its errors as well as its evidence.
