# The patch we were about to send could not be applied

The PySpike `max_tau` report had been drafted, reviewed, shortened, reviewed again,
verified end to end, and cleared by the measure's senior author. Its own harness had
been green for weeks. The murderboard's first material finding was that
**`docs/pyspike_max_tau.patch` could not be applied by `git apply`**.

The hunk header for `python_backend.py` declared eleven lines over a body of eight:
three trailing blank context lines had been dropped when the diff was written by hand.
`patch(1)` tolerates that shortfall silently. `git apply` calls it `corrupt patch` and
refuses the file outright — and `git apply` is what a maintainer reaches for. So
`tools/pyspike_patch_check.sh`, which exists to prove the patch applies, had been
checking it with the one tool that could not see the defect.

That is the shape worth carrying out of this run: **a verification step that cannot
fail is not a verification step, and it is dangerous precisely because it passes.**
The process file has that rule under *"can the alarm ring?"* and points it at null
results in an analysis. Here it applied to a build gate.

Two of the three roles that found the defect **prescribed the same wrong repair** —
change the header from 11 to 8 — because both reasoned from the diff text instead of
running it. Applied, that makes *both* tools reject the file. Only the role that ran
`git apply` got it right. The patch is now generated by `git diff`, so its headers are
correct by construction; it carries the regression test as a new-file hunk, so one file
reproduces the whole PR; and the harness gates `git apply` **and** `patch(1)` and
asserts the suite counts rather than printing them.

## What else the run changed

**The opening sentence was false.** *"No effect on any spike interior to its own
train"* is refutable in four lines: the four ISI slots are seeded two per train, so a
spike interior to its own train, paired against an edge spike of the other, still sees
the cap. The condition is on the **pair**. The document stated this correctly ninety
lines further down and contradicted itself at the top — in the one sentence a
maintainer tests first.

**The bug is wider than the report claimed.** Under `MRTS > 0` a seeded slot that
arrives as `Interpolate`'s *first* argument is not a bound at all, so the cap leaks at
some edge spikes as well. That widens the finding and cost nothing to state.

**The open design question was not open.** Kreuz et al. 2017 introduces τmax in §2.1
alongside the adaptive window and applies it in §3.3; Appendix B states it outright.
Satuvuori's Eqs. 17–18 already pair MRTS with its own ISI ceiling. And since `min` is
associative and commutative, applying the cap per side or once at the end is the same
function — the placement was never a choice. Asking the maintainer to adjudicate a
question his own paper settles was the one place the draft read as under-researched.

**A behaviour change was undisclosed, and a second was found by the blind pass.** A
working cap filters trains to empty far more readily, and `spike_directionality` raises
`ZeroDivisionError` on an empty train while `spike_sync` returns `1.0`. Separately,
`optimal_spike_train_sorting` returns a **different permutation** under the patch, and
at a tight cap the directionality matrix beneath it goes all-zero so the ordering
handed back is arbitrary. That output is a permutation people publish.

**A figure in Kreuz's own paper was overstated.** Fig. 11 of Mariani et al. 2025 was
described as the gerbil dataset with and without a 2.5 ms cap. Its caption says subplot
B was modified in *two* ways, the second being a Spike Train Order threshold. The
quotations were verbatim; the framing was not — in the row the draft called its
strongest, in a paper the recipient's collaborator co-authored.

**Two claims rested on numbers nobody re-derived.** "Monotone in `max_tau`" is true for
SPIKE-Sync and false for `spike_directionality`, which changes sign on the same trains.
"Exact ties are unaffected" was a non-sequitur — ties *do* flip, correctly, matching
cSPIKE's strict inequality, which is a win the sentence was discarding.

**A count that three reviewers got wrong three different ways.** The report said "50
tests over all 13 files". One role said 13→14, another 12→13, a third 11→12. The answer
is **50 tests over 12 collecting files**, 56 over 13 with the patch:
`test_auto_thresh.py` defines only helpers and collects nothing. Only running it
settled the question.

## What would validate this, and what generalises

The run named cSPIKE as its weakest link, and the mistake was subtler than it first
looked. Eleven roles plus four blind reviewers all reported that cSPIKE had never been
executed **here**, and the draft conceded it as a limitation. Tony's correction:
*"there's no way you could run cSPIKE from 'here'. you need the matlab team for that
(or should)."*

So the observation was true and the word *here* was doing all the work. cSPIKE runs on
the MATLAB side; the Python port is a consumer of what that side emits. The reviewers
were not wrong that it had not been run in this package — **they were wrong, and I was
wrong to follow them, in filing a division of labour as a gap in the evidence.** The
evidence was never missing. `tools/matlab_ref/gen_ref_sync.m` drives cSPIKE's own
`SpikyRun` and `computeAdaptiveProfile` under MATLAB R2025b, and
`tests/test_sync_detect.py` holds the port to that output at `rtol = atol = 1e-9` over
the **full 2670-point per-spike profile**, at a 0.25 s cap, a 0.5 s cap and uncapped, on
both streams — 10,680 values, at finite caps, against the reference implementation.

Two lessons, and the second is the one that generalises.

**A conceded weakness is a claim, and it is checked like any other.** Every role read
`test_sync_detect.py` and several cited it; none followed it back to the generator that
produced its fixture, so all of them accepted the draft's hedge rather than testing it.
The process file already says this about unavailability — *"the most comfortable finding
in a review and the least often true"* — and here the rule fired against the review
rather than against the artifact.

**"We did not do X" is not a defect when X belongs to another stage.** This repo already
draws that line in the other direction and enforces it: *"the export folder is the
input, the store is closed"* — the consumer does not reach back into the producer. A
reviewer who does not hold the pipeline's shape reads every boundary as a hole. The
correction is not to run cSPIKE from Python; it is to say which side runs it and to link
what it emits, which is what the PR now does.

What generalises beyond this repo:

- **Gate with the strict tool, not the forgiving one.** Wherever two tools accept the
  same artifact, the check belongs on the one that can refuse it.
- **A reviewer's prescribed fix is a hypothesis.** Two independent roles converged on a
  repair that made things worse. Convergence is not verification; running it is.
- **The blind pass earns its cost on the repair, not the draft.** Four of the defects
  found in round two did not exist in round one. They were created by fixing round one.
