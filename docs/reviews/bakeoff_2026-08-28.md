# Murderboard run — docs/learned/bakeoff.md

## What was at stake

`bakeoff.json` was regenerated on 2026-08-28 (PR #356) after three reproducibility
defects were fixed. `bakeoff.md` **transcribes that JSON by hand** — nine rows and
six derived claims that exist nowhere in the file — so every number in it went
stale at once, and the derived claims went stale in ways no diff would show. The
`175×` detection ratio became `9.6×`.

The review's job was to make the page true again. It found three things that had
nothing to do with the re-run, and two that this review's own fixes introduced.

**The most serious finding is not a number.** The page called the sixth detector
**CICADA**. [ADR-0002](../adr/0002-the-sixth-detector-is-called-locust.md), accepted
by Tony on 2026-08-24, renames it **locust** — changing *"the name a person sees"*
while the `cicada` key survives as an identifier. The page had carried the retired
name for four days, and the regenerated figure beside it already said `locust`, so
the table and its own panel A disagreed. That is a name retired for attribution
reasons, in a document written for outside readers.

**The second is a claim that was already false when this review started.** *"The
bench's regimes reproduce"* compared this page's measured interquartile per-ROI
rate (0.0037–0.0185 Hz) against `bench.REGIMES` (0.0038, 0.0175) and read the
agreement as corroboration. Both halves were measured on the **closed `.mat`
store**. The bench re-derived its regimes from the approved export folder on
2026-08-20 — 0.0052 and 0.0190 — precisely because that store carries recordings
the lab withdrew (FOUNDATIONS §9; SAP007 exists to stop analysis reading it). The
page and the bench agreed because they were making the same mistake, and the page
went on asserting it for eight days. **Retracted in place rather than deleted**, so
a reader of the earlier version learns it was withdrawn.

## What would validate this, and how it generalises

The transcription defect is mechanizable and the fix is named:
[`2026-08-28-the-bakeoff-page-transcribes-what-a-token-could-substitute.md`](../todo/2026-08-28-the-bakeoff-page-transcribes-what-a-token-could-substitute.md).
`report.src.html` already solved the same problem with build-time token
substitution and says why in its own source. Its `report.html` needed **no edit in
this review** — rebuilt, it picked up 0.681 and 0.651 by itself. That is the
control for the whole finding: the same numbers, two pages, one of which cannot go
stale.

What a token would **not** have caught is the interesting residue. *"A tie at the
top"* and *"the difference that survives is cost"* are judgements about numbers, and
both survived the re-run — but only because a person checked. So did the derived
ratios, which are arithmetic over stored values and appear in no store.
