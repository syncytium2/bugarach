## Findings — location · issue · severity · fix · verified

**F1. The gap grid is re-derived by hand, and the page's sentence about it is false as written — major — verified: yes**
- Location: `tune_net_merge_gap.py:70-72` (`GAPS_SEC = (0.0, 1.0, 2.0, 3.0, 5.0, 8.0, 15.0, 30.0)`, and the same claim in its docstring); the sentence is `build_net_merge_gap_page.py:361-363`, rendered as *"It holds every gap CoactDetect's own grid offers (0 to 8 s) and runs to binned SCE's top, 30 s, so a net can reach any gap a coded detector was allowed."*
- Issue: the run declares the coded merge-gap grids in `meta.json declaration.hand_axes`. They are coact `[0, 1, 2, 3, 5, 8]`, **loco `[0.5, 1, 2, 4, 8]`**, **sce `[0, 5, 10, 15, 20, 30]`**. The union is `{0, 0.5, 1, 2, 3, 4, 5, 8, 10, 15, 20, 30}`; `GAPS_SEC` misses **0.5, 4, 10 and 20 s**. So "a net can reach any gap a coded detector was allowed" is not true — four of the twelve allowed gaps are unreachable. The tool's own test only checks the **top** (`test_the_gap_grid_reaches_every_gap_a_coded_detector_was_allowed` asserts `max(coded_tops) <= GAPS_SEC[-1]`), which is why the gap between the sentence and the grid survived.
- Practical impact is small: chosen gaps are 8 s in 26 of 32 choices per draw, and none sits at a grid end (`gap_at_grid_edge` false everywhere) — but the sentence claims a property the grid does not have.
- Fix: either derive the grid as the sorted union of `decl["hand_axes"][d]["merge_gap_sec"]` (plus 2.0), and assert that union is covered; or reword to "spans the range of gaps the coded detectors were allowed, 0 to 30 s, at eight values" and say the grid is coarser than theirs.

**F2. The noise scale — the page's decision rule — is a hand-carried constant with no computed source — major — verified: partially**
- Location: `tune_net_merge_gap.py:79` (`NOISE_F1 = 0.010  # median F1 change from a recordings-only change (WSMIP065)`), consumed at `build_net_merge_gap_page.py:155, 207, 298, 323-324, 484, 497, 513-518`.
- Issue: this number decides what the page calls a result ("a mean inside it is not a result"; the lede's *"the lead clears that scale"*; the shaded band in Figures 1 and 2; `set_aside_leads`). Nothing in the tree computes it: its only source is a prose line in `docs/goals/learned-model-family.md:69-70` ("the nets by a median of **0.010 F1**, the coded detectors by **0.003**"). No `claim()` and no test ties it to any file, so it cannot go stale loudly — unlike every other directional sentence on this page.
- It is load-bearing at the margin. The replicate's set-aside leads are **+0.0150** (`chorus_norm`) and **+0.0133** (`chorus_gain_norm`) — above 0.010, so the page says they clear the scale. An indicative recomputation from the page's own two draws (median |this − replicate| of the as-run held-out fold means, n = 32) gives **0.017**, above both. That population is *not* the one the goal page measured (the two draws each chose their own configurations, whereas the 0.010 held configurations and training seeds fixed), so this is a flag, not a refutation — but the page gives a reader no way to tell which population its yardstick came from.
- Fix: compute the scale from `replicate_summary.json` / the run's results by the stated rule (same configuration and training seed, recordings swapped), write it into the JSON with the rule that produced it, and put the value behind a `claim()`; or, at minimum, state the population in the caption and cite the goal page.

**F3. The tool reuses the reference by injecting an unlanded branch onto `PYTHONPATH`, and records no version of it — major — verified: yes**
- Location: `tune_net_merge_gap.py:9-11` (docstring), `:82-88` (`_tool()`), `:129-136` (`_load`, which does `tr.model.to("cuda")`), `:176-177` (`pick_threshold(tr.model, ...)`), `:644-659` (the output document).
- Issue: `tune_learned_vs_coact` and `bugarach.learn.train.probabilities` exist only on branch `tune-bench-comparison`. In the worktree the tool is committed to, `src/bugarach/learn/train.py` has **no `probabilities`**, and its `pick_threshold` builds a CPU tensor directly (`torch.from_numpy(enc.raster).unsqueeze(0)` at `:276-279`) while `_load` has just moved the model to CUDA — so run from its own tree the tool cannot work, and the version that does work is whatever happens to be checked out elsewhere at the time. Section 8 of the page tells a reader the arrays "regenerate … in about two hours", which no one can do from this repository.
- Fix: record the `tune-bench-comparison` commit, torch version and host in the output document (as the run does), and add the branch/commit to section 8. Better: land `train.probabilities` (it is the device-crossing point all three callers need) so the scoring path is testable in this tree.

**F4. The crowded veto's NaN handling is inverted relative to both canonical implementations — minor (latent; verified not firing) — verified: yes**
- Location: `tune_net_merge_gap.py:427-440` (`Selector.crowded`, which returns `self.T.objective(items, m)`) and `:462-477` (`choose`: `ok = cr >= ref - self.max_drop`).
- Issue: `T.objective` maps a non-finite pooled F1 to **0.0** (`f1_or_zero`). Goal 1's rule refuses a candidate whose crowded score is not finite (`search_all_settings.make_admissible`, `search_all_settings.py:287-291`: *"Not scored there = not admissible"*), and the coded side's after-the-fact check requires **both** sides finite (`crowded_check_fair_comparison.py:99-101`: `math.isfinite(f1) and math.isfinite(ref) and f1 >= ref - MAX_CROWDED_DROP`). Here, if the **reference** (the as-run choice at 2 s) ever pools to a NaN F1 on a crowded background — no calls at all, which is exactly what the collapsed chorus refits do — `ref` becomes 0.0 and `cr >= -0.02` passes **every** candidate: the veto switches itself off silently, in the direction that admits. The comparison orientation (`>=`, `ref - drop`) and the constant (`bench.MAX_CROWDED_DROP`, imported) are otherwise correct.
- I checked both committed draws: no `crowded_f1` or `reference_crowded_f1` is 0.0 or missing, so no published number moves.
- Fix: refuse a move when `crowded()` is not finite on either side, as the two references do — or, better, factor the comparison into `search_all_settings` (round 3's F6 already suggested a `crowded_veto(got, ref)`) and call it from all three places.

**F5. `NB_FACTOR` hardcodes the four-fold value where the report derives it from the declaration — minor — verified: yes**

- Fix: `from build_fair_comparison_report import _nb_factor` (the page builder already imports twelve names from that module) and compute it from `decl["folds"]`; have the test read the factor from the same function.

**F6. `_paired` is now the fourth copy of the paired statistic in the tree, and it differs from one of them at the edge — minor — verified: yes**

**F7. The stored row drops `by_frac` and collapses `tol_sec`, defeating `pool_scores`' mixed-tolerance guard — minor — verified: yes**
- Location: `tune_net_merge_gap.py:74` (`FIELDS`), `:144-154` (`_rows`, which keeps only the last score's `tol`), `:323-325` (`Scored._row`, `dict(zip(FIELDS, …), by_frac={}, tol_sec=tol)`); reference `tune_learned_vs_coact.py:520-526` (`score_row`, which stores each `Score`'s own `by_frac` and `tol_sec`).
- Issue: one `tol_sec` is read off the last recording scored in the file and stamped onto **every** row read back, so `bench.pool_scores`' refusal to pool scores measured at different tolerances (`bench.py:1285-1291`, written precisely because "the failure would be invisible, since counts add whatever they were counted against") can never fire on this path. Dropping `by_frac` is harmless for the objective — I checked that `pool_scores` only accumulates it and `objective`/`probe_rates` read none of it — but it means this file cannot feed the parent report's per-participation breakdown. Today every call uses `score_stream`'s default `tol_sec = score.TOL_SEC = 2.5`, so nothing is mixed.
- Fix: store the per-row tolerance (one more `float32` array, or assert in `_rows` that all scores share a tolerance and record the assertion in `meta`).

**F8. The threshold grid is read from live code and never checked against the run's declaration — minor — verified: yes**
- Location: `tune_net_merge_gap.py:139-141` (`_grid()` → `train.THRESHOLD_GRID`), used to interpret the run's recorded `own_index` (`:182`) and `sel["threshold_index"]` (`:505`).
- Issue: those indices were written by a run on another branch; `meta.json declaration.threshold_grid` records the grid they index into. A grid that has since changed length or spacing would re-point every gated selection at a different threshold, silently. The `own_index` reproduction check would catch some of that but not all (a re-ordering that preserves the argmin). The reference has the same weakness, but it always ran against its own live code; this tool runs against a stored run and so is materially more exposed.
- Fix: one line — `assert _grid() == [float(t) for t in decl["threshold_grid"]]` in `Selector.__init__`, reported in the output's `reproduction` block.
