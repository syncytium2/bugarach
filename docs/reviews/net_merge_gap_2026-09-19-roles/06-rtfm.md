## Answers to the five questions asked

1. **Is the gap selected without touching held-out data?** Yes. `Selector.inner` reproduces `_inner` exactly (for each `j` in the training folds, the fit trained on the other two, over `tune_seeds` — 9 distinct fits, no duplicates), the crowded recordings are `make_tail_recording` seeds 1–12 (disjoint from the bench's 1000–1023), and `pick_threshold` reads only the fit's own validation block. No leak found.
2. **Is the threshold rule at each gap the same rule the run used?** Yes. `train()` calls `pick_threshold(model, mk, dt, seed, stream)` with `merge_gap_frames=20` defaulted; the tool calls the identical function with the same `mk` (built from `run.json`'s recording list, in order), same `dt`, `seed`, `stream`, same default `n_val=4`, varying only the gap. Verified empirically: `own_threshold_at_2s == fits` for all 1938 + 1943 fits.
3. **Is the crowded check applied the way goal 1 applies it?** Mostly yes — same builder, same `N_TAIL=12` seeds, same two backgrounds, same "mean of the two backgrounds' pooled F1" (`objective` groups on `tail_quiet`/`tail_busy`), same `MAX_CROWDED_DROP=0.02`, same "reference = the setting the choice replaces". The `first passing candidate in descending inner-F1 order` is equivalent to goal 1's `filter-then-best`. What is **not** carried over is goal 1's reason for the veto: see findings 1, 4, 5.
4. **Is pooling done through the project's own `pool_scores`?** Yes — `T.objective` → `T.pooled` → `bench.pool_scores`, never re-derived. `probe_rates`, `within`, `quiet_rate`, the per-fold `budgets` and the tie-break ranks are all the tuning tool's own functions/values. `by_frac` is dropped from the stored rows, which is harmless (F1 does not read it) and `tol_sec` is uniform, so `pool_scores`' mixed-tolerance refusal cannot mis-fire.
5. **Are the statistics right, and the correction correct?** The estimator is right: `_paired` matches the run's `_paired` line for line, and `NB_FACTOR = sqrt(3/7)` is exactly `build_fair_comparison_report._nb_factor(4, 1/3)` = √((1/4)/(1/4+1/3)), the right Nadeau–Bengio factor for 4-fold CV with one fold held out. df = k−1 = 3 is the conventional choice. The problems are in what is reported around it (findings 2, 3, 14).
6. **Does the page's stated method match the code?** Substantially yes; the divergences are findings 6, 7, 10, 11, 12.

## What checked clean (worth recording)

- **Reproduction at the shipped settings.** The validation exercises the production configuration, not a looser one: at 2 s the re-decoding reproduces *every* one of the 3,881 saved fits bit-for-bit — picked threshold, per-recording counts, empty-recording call counts — and the inner and held-out F1 deltas against the run's own `results.json`/`selections/` are exactly 0.0 in both draws. That is the strongest single fact on the page and it is correctly earned.
- **Rule reuse is real, not paraphrased.** `objective`, `pooled`→`bench.pool_scores`, `probe_rates`, `within`, `quiet_rate`, `score_path`/`recs_hash`, `_planted`/`_empty`, `probabilities` are imported from `tune_learned_vs_coact`, not re-derived. Tie-break ranks match `select_learned` exactly (`f1, −n_params, −steps, −draw_index` ungated; with `threshold` inserted before `−draw_index` gated), with `−gap` appended as a new last key. Budgets come from `meta.json budgets[h]` per fold.
- **Fold structure.** `Selector.inner` reproduces `_inner`; `fold_rids`' contiguous slicing is right because `bench.fold_split` deals contiguous folds; `recs_hash` is order-independent so `score_path` resolves despite `fit_recordings` vs `fold_recordings` ordering.
- **Units and grid.** `decode`'s merge is end-of-run-to-start-of-next in frames; `sliding.merge_runs` is end-to-start in seconds — the same rule, so "matched gaps" is a fair comparison. `GAPS_SEC` contains all six of `FULL_GRIDS["coact"]["merge_gap_sec"]` = (0,1,2,3,5,8) and reaches `FULL_GRIDS["sce"]["merge_gap_sec"]`'s top of 30. `int(round(g/dt))` is exact at every grid value. `TAIL_RECORDING` inherits `duration_sec=10800.0`, so "24 three-hour recordings, seeds 1 to 12 at both backgrounds" is correct, and matches `search_all_settings.N_TAIL = 12` and its `TAIL` pair.
- **Counts the prose claims match what they count.** "3,881 saved fits" = 1938 + 1943; "nine inner fits (three training seeds, three inner folds)"; "five outer refits" (`n_seeds == 5` for every fold in both draws); "1 of the 40 / 3 of the 40" chorus refits under 0.2 F1; "59 of 64 moved off 2 s"; "CoactDetect chose 8 s in every fold". All recomputed and correct.
- **`LOW_F1` set-aside rule** is byte-identical to `fair_comparison_evidence._refit_health`'s (`f1 >= 0.2`), so "as the report does" is accurate.
- `tests/test_tune_net_merge_gap.py` exists and does gate the reproduction, the move rule's `min_gain` and crowded conditions, the NB factor, and the grid's reach.
