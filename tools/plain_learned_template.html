The learned detectors

A companion to Finding cells that act together: four programs that were not written as steps, but trained on examples.

Read the main document first. This one is held back deliberately. The six step-by-step programs are being reviewed, and the networks were set aside so that review can finish on one kind of program at a time. Nothing here has been through that review.

1. What a learned detector is

The six programs in the main document are algorithms: a person wrote out the steps, and the computer carries them out in the same order every time. The four here are not. Each one is a small neural network — a stack of simple arithmetic operations, each holding numbers the computer can adjust.

We showed a network many simulated recordings whose answer we knew. After each example the computer nudged those numbers so the network's output rose at the planted coordinated events and fell everywhere else. That nudging is training. When training ends the numbers are fixed, and the network runs like any other program: event times in, calls out. Nobody wrote a rule about 2-second bins or shifted copies; whatever the network does instead is in those {{T.tube_params}} numbers.

2. What happens inside one

The design is called tube, from the picture its author had in mind: looking down a dark tube while the recording slides past, a coordinated event goes by as a sudden jump. What the network is given is the same raster the six algorithms get — no pictures, no cell identities, just which cell had a calcium event when.

There are four versions. tube is the one drawn above. tube-guard ignores the share of cells with events immediately around the moment it is scoring, so a real event cannot inflate its own comparison. tube-ratio divides by the surrounding share instead of subtracting it. tube-ratio-guard does both.

3. How they score

On the quiet background tube-guard reached {{T.f1q_tube_guard}} and tube {{T.f1q_tube}}, which sits alongside the best of the six algorithms (CoactDetect {{T.f1q_coact}}, LoCo {{T.f1q_loco}}). The two ratio versions scored lower: tube-ratio {{T.f1q_tube_ratio}} and tube-ratio-guard {{T.f1q_tube_ratio_guard}}.

The spread between training runs is the thing to notice. The same design, trained three times on the same recordings, lands in different places — {{T.f1q_tube}} on average for tube, but its worst and best runs sit far apart. An algorithm has no equivalent of that: run it twice and it does the same thing.

4. Busy stretches, where they were taught the wrong lesson

Every one of these networks was trained on recordings in which the busy stretch never held a coordinated event. That was a decision about how to build the training set, and the networks learned it as a fact about the world. tube finds {{T.out_tube}} of mid-sized events outside a busy stretch and {{T.in_tube}} inside it. The two ratio versions find {{T.in_tube_ratio}} and {{T.in_tube_ratio_guard}} inside — nothing at all — while making almost no false alarms there, which looks like excellent behaviour until you notice they cannot see anything in a busy stretch either way.

This is the clearest difference between the two kinds of program. When an algorithm goes blind in a busy stretch, it is because of a rule someone wrote and can read back. When a network does, it is because of what it was shown.

5. What would have to happen before these are usable

  • Training sets that contain busy stretches with real events in them. Until then the blindness above is baked in.
  • More than one training run per design, reported together. A single run's score is not a property of the design.
  • A check on real recordings that does not depend on the simulator, which the main document shows is imperfect in ways that matter.
  • An account of what the network responds to. Figure 1 shows the stages, not the reasons; for an algorithm those are the same thing, and here they are not.
